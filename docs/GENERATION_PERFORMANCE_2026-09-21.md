# 生成链路性能优化

## 已实施

1. 今日方案的早期复用检查与后续完整生成，可能重复读取已选产品的正式知识、研究草稿、成分数据。`createTodayProductKnowledgeReadService` 现在在服务实例内部复用成功的完整读取，只查询新增产品。生产调用处在每次鉴权后的请求中创建实例，没有模块级或跨用户缓存。三个查询及证据投影全部成功后才标记可复用；失败可以重试，未知成分仍保持未知。
2. 购买分析的资产成分读取与使用历史读取并行执行；仍等待两者完整返回后计算和保存。没有改评分、输入或保存规则。

## 保留的质量边界

- 不修改模型、提示词、输出 token 上限或输入上下文。
- 不提前向用户展示未经校验的护理决策，不将部分数据当作完整安全依据。
- 方案模型先产生决策，说明模型使用已校验决策生成解释；两者有数据依赖，不强行并行或合并。
- 皮肤对话已经使用 SSE 流式回复；仅“开启流式”不是新的优化。
- 日记解读已经按事实复用缓存；冷缓存模型耗时仍然存在。

## 验证及限制

- 21 个测试文件、233 项相关测试通过，涵盖护理方案、安全、购买分析和方案 API。
- 新测试验证选中产品只查一次、扩展集合只查新增项、失败重试、实例隔离、未知知识语义及与未复用结果的一致性。
- 购买分析增加受控等待测试，确认成分查询未完成时使用历史已开始读取，且不会提前保存；修改后该文件复跑通过。
- 生产构建（含类型检查）通过，修改的服务文件 ESLint 通过。
- 未部署，未使用真实登录会话计时，不宣称具体提速比例。本轮未重跑全库测试，上一轮记录的样式断言及 lint 遗留问题仍存在。

## 后续定位顺序

应在生产模式记录同一次请求的鉴权、数据库、知识读取、记忆检索、模型首段输出、模型完成、校验及保存耗时，再判断瓶颈。代码已有不少开发环境计时，但不能把开发编译时间当作生产延迟，也不能把首段输出提前当作总生成时间缩短。

如果时间主要花在数据库或服务间通信，可再核对部署位置和查询执行情况；如果主要花在模型，则需要真实样本做质量对照后评估供应商或配置调整。此轮未更换模型、区域或部署配置。
